# Internationalization

The supported locales are `pt-BR` and `en-US`. Interface language and Advisor response language are separate user choices and must remain independent.

## Frontend strings

Locale resources live under `frontend/src/i18n/<locale>/` and are split into `common`, `datasets`, `experiments`, `expert`, `training`, `advisor`, `decisionLab`, and `howItWorks` namespaces. Add the same key to both locales and render it with `useTranslation`; do not place user-facing prose directly in TSX.

The UI locale is stored as `uiLanguage` in `localStorage`, updates the document `lang`, and falls back to English for a missing key. The Advisor selection is stored separately as `llmLanguage` and sent in recommendation/Auto requests.

Run:

```bash
make test-frontend
make lint-frontend
```

The i18n test verifies locale parity. For visible changes, also switch the complete workflow in both languages and check labels, validation errors, status text, charts, empty/loading/error states, and responsive layout.

## Backend prompts and errors

Advisor system prompts live at `backend/prompts/<locale>/advisor_system.txt`. `AdvisorPromptBuilder` selects a supported locale and requests the answer in that language. Prompt changes must remain structurally equivalent across locales and must not request raw rows unless sample sharing is enabled.

API errors intended for the UI use stable codes or `message_key` values; clients translate them locally. Internal exceptions and provider text should not become untranslated UI copy or expose credentials. Persist semantic values and locale context, not already-translated presentation strings.
